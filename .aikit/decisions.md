# Decisions

Why this project is built the way it is, oldest first. One entry per decision that changes a
contract, a dependency, a data format or the architecture; IDs are consecutive and never reused.

### ADR-001: The Pebble v1 language surface is frozen, and every failure carries a position and a fix
- **Date**: 2026-10-18
- **Status**: Accepted
- **Context**: Pebble is built as an AIKit evaluation project: the test is whether the governance process (plan, checkpoints, frozen surface, gates) produces a small language without silent scope creep. A language's surface is a contract, and without a written freeze it grows every session. Separately, the project carries AIKit's error-UX rule: every user-triggered failure must explain why it happened and how to fix it.
- **Decision**: Freeze the v1 surface. Values: int, float, bool, string, list, and none (the absence of a value, added so effectful functions and failed lookups have a representable result; recorded here as the one clarification of the draft plan). Statements: let, assignment, if/else, while, for-in, fn, return, blocks. Operators: + - * / % ^, comparisons, and/or/not, calls, indexing, list literals. Builtins: print, len, range, str, int, floor, min, max, abs. Interfaces: file runner, -e, REPL; exit codes 0/1/2. Every lexer, parser and runtime error renders as file:line:col plus Why and Fix, pinned by a meta test. Non-goals: classes, modules, closures, exceptions, unicode identifiers, break/continue, slices, script arguments. Additions to the surface require a new task and a new ADR.
- **Consequences**: The surface is small enough for one task with six milestone slices, and any silent drift is visible against this record. Error quality is a tested contract rather than a style goal. Cost: unlisted conveniences (slices, break/continue, float()) are refused on purpose; users wait for a later task, and the refusal itself is the evaluation signal.

### ADR-002: Builtin semantics and the value display form are fixed for v1
- **Date**: 2026-10-19
- **Status**: Accepted
- **Context**: ADR-001 lists nine builtin names but not their contracts. Without a written decision, arity, coercion and display details would drift with each edit, and the CLI and REPL would have no stable output to target.
- **Decision**: Builtins are visible in the global scope and may be shadowed by a later `let`. A builtin checks its arity before evaluating arguments and reports the call's position. `print(x)` writes the display form plus a newline and returns none. `len` accepts a string or list. `range` accepts `range(stop)` or `range(start, stop)` with int arguments only (bools excluded), is half-open, and has no step. `str(x)` is the display form. `int(x)` accepts an int, a float truncated toward zero, or a string of an optional `+`/`-` sign and ASCII digits; non-finite floats and bools are refused. `floor(x)` accepts an int or finite float and returns an int. `min`/`max` accept one or more values, or exactly one list of values, and order numbers with numbers or strings with strings; empty input, bools and mixed kinds are errors. `abs(x)` accepts a number. The display form is: `true`/`false`, `none`, `str(float)` for floats, bare text for a top-level string, and `[a, b]` for lists with nested strings double-quoted and `\\`, `"`, newline, tab and carriage return escaped; functions display as `<fn name>` and builtins as `<builtin name>`.
- **Consequences**: All nine names now have testable semantics, so `print` output is a stable CLI/REPL contract rather than an incidental Python `repr`. Costs: no `range` step, no whitespace-tolerant `int(" 42")`, and `min`/`max` deliberately do not order lists; those conveniences wait for a later task.

### ADR-003: v1 caps host-sized resources and turns every host arithmetic failure into a Pebble error
- **Date**: 2026-10-19
- **Status**: Accepted
- **Context**: Hardening found programs that reached Python tracebacks: `0 ^ -1` (ZeroDivisionError), dividing huge ints (OverflowError), printing an int beyond Python's decimal-conversion limit (ValueError), integer literals beyond that limit, and `range`/repetition large enough to exhaust memory. ADR-001 promises that user failures never surface as tracebacks and that errors explain themselves, so the runtime needs explicit limits rather than host behaviour.
- **Decision**: Resource limits live in `limits.py`: call depth 100, integer exponent 10,000, an int of about 4,000 decimal digits (13,280 bits), and a range or repeated sequence of at most 1,000,000 values; a float literal must be finite. An oversized literal or numeric string is a positioned LexError or EvalError, and an arithmetic result over the int cap is an EvalError. `0` raised to a negative power and a division result beyond the largest float are EvalErrors. As a final shield, the CLI converts any unexpected host exception into a three-line internal-error report with a Why and a Fix and exit code 1, never a traceback.
- **Consequences**: Programs have predictable memory and output bounds on every host, and the error-format meta test can assert the three-line form for all three error classes. Costs: arithmetic and ranges beyond the caps are refused (`2 ^ 10000` is allowed, `10 ^ 10000` is not), and larger values wait for a later task.

### ADR-004: v2 adds loop control, slices, a range step and float()
- **Date**: 2026-10-19
- **Status**: Accepted
- **Context**: ADR-001 froze the v1 surface and named break/continue, slices and float() as non-goals, and ADR-002 recorded the missing `range` step as a deliberate cost. The v1 evaluation task is complete and green, and the first conveniences users miss are exactly those loop exits, subsequences and number conversions. Adding them trades a small, bounded amount of surface for real scripting power, so the change needs its own record before any code.
- **Decision**: Add two statements, `break` and `continue`, valid only inside a `while` or `for` body; they affect the innermost loop, and a `fn` body is not inside any enclosing loop, so loop control can never cross a call. Using either outside a loop is a parse error at the keyword. Add slices `target[start:stop]` and `target[start:stop:step]` for lists and strings, with any part omitted; indices must be ints (bools refused), the step defaults to 1 and may not be 0, negative indices count from the end, bounds are clamped, and omitted ends follow the step's direction; the result is a new list or string, and the target must be a list or string. Extend `range` to `range(start, stop, step)` with int arguments (bools refused), a nonzero step, half-open and sign-aware walking, still capped at 1,000,000 values. Add the tenth builtin, `float(x)`: it accepts an int, a float (returned unchanged) or a decimal string with an optional sign, digits, optional fraction and optional exponent; bools, whitespace, non-decimal strings and results that are not finite are refused, and an int too large for a float is an EvalError. This amends ADR-001's non-goals and ADR-002's builtin count; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: Scripts can leave a loop early, skip an iteration, take a subsequence of text or a list, count with a step and convert numeric text to a float, each pinned by failing-first tests. Costs: the surface grows by two statements, one expression form, one builtin and one `range` arity; slice step is the subtlest rule (`[a:b:0]` and boolean bounds are refused with a position); a function cannot break an outer loop and must return a value instead; classes, modules, closures, exceptions, unicode identifiers and script arguments remain non-goals.

### ADR-005: Script arguments exposed as a global 'args' list of strings
- **Date**: 2026-10-19
- **Status**: Accepted
- **Context**: ADR-001 and ADR-004 marked script arguments as a deliberate non-goal. Without command-line argument passing, Pebble scripts cannot easily be parameterized from shell invocations, limiting batch scripts, tools, and automation. Users expect to pass arguments to scripts run via file, `-e`, or standard input, and to access those values directly within the Pebble runtime.
- **Decision**: Expose script arguments via a predefined global variable named `args`, containing a list of strings (`list[str]`). The `Interpreter` constructor accepts an optional `args` sequence (defaulting to empty list `[]`). When running in the REPL or without CLI arguments, `args` defaults to an empty list `[]`. In the CLI runner, any positional arguments following `FILE`, `-e SOURCE`, or `-` (or following the `--` option terminator) are collected as strings and passed to the interpreter as `args`. Attempting to call `args()` as a function raises a positioned `EvalError` whose fix explains that `args` is a list of strings and suggests indexing `args[0]` or iterating `for arg in args`. This amends ADR-001's and ADR-004's non-goal regarding script arguments.
- **Consequences**: Pebble programs can inspect `len(args)`, index elements with `args[i]`, iterate with `for a in args`, and slice arguments with `args[start:stop]`. The language surface gains no new keywords or syntax; `args` is simply a predefined list in the global scope that behaves according to standard list semantics and may be shadowed by `let args = ...` if desired. Costs: `args` is a reserved initial global variable name; calling `args()` is refused with an explanatory positioned error; classes, modules, closures, exceptions, and unicode identifiers remain non-goals.

### ADR-006: Arithmetic never produces a non-finite float
- **Date**: 2026-10-22
- **Status**: Accepted
- **Context**: ADR-003 already required a finite float literal and refused a non-finite `float()` conversion, and `int()`/`floor()` refused non-finite inputs. A review found the gap between those guards: `+`, `-`, `*`, `/`, `%` and `^` let a finite result overflow to `inf` or produce `nan`, for example `float(10 ^ 308) * 10`. Pebble has no literal spelling for either value, so a program could reach a state it cannot express in source and carry it into comparisons and remainder.
- **Decision**: Every float arithmetic result must be finite. `+`, `-`, `*`, `/`, `%` and `^` check their result; an overflowing float is a positioned EvalError with the message "the result is too large for a float", and `nan` is refused with "the result is not a number". A finite result at the edge of the float range is still allowed. The existing `int()` and `floor()` non-finite guards remain as defensive builtin contracts for embedders, but ordinary Pebble source can no longer reach them.
- **Consequences**: Every user-reachable float is finite and spellable, and overflow fails loudly instead of propagating a value with no source form. Costs: an accidental IEEE-style workflow that expected `inf` must guard its magnitudes; the finite-float guards are duplicated by design in the evaluator and in `int()`/`floor()`.

### ADR-007: Loops do not introduce a scope
- **Date**: 2026-10-22
- **Status**: Accepted
- **Context**: The evaluator has one global scope plus one frame per call, and no block scope: `if`, `while` and `for` bodies execute in the current scope. `_execute_for` binds the loop variable with the same `_define` used by `let`, so the last item stays visible after the loop. That follows the documented scope model, but neither an ADR nor a test stated it, leaving the behaviour easy to mistake for a defect or to change silently.
- **Decision**: A `for` loop does not create a scope. Its loop variable is an ordinary binding in the enclosing scope, as are `let` declarations written inside a loop or an `if`/`while` body, and it remains after the loop finishes. Tests pin all three cases: a loop-only variable is visible afterwards, a `let` inside a loop body survives, and a loop reuses and overwrites an existing name. Changing this rule requires a new ADR.
- **Consequences**: Scoping stays uniform and cheap to reason about: one global scope plus call frames, no hidden block frames. Costs: loop variables behave unlike Python's, and a second loop in the same function intentionally reuses the same binding rather than shadowing it.

### ADR-008: Range length is computed with integer arithmetic, so huge bounds stay a Pebble error
- **Date**: 2026-10-22
- **Status**: Accepted
- **Context**: ADR-003 caps a range at 1,000,000 values before building it, and ADR-001 promises that user failures are positioned Pebble errors rather than host errors. `_range` checked the cap with `len(range(start, stop, step))`, and Python raises `OverflowError` when the count does not fit its C index type. A legal program such as `range(10 ^ 100)` therefore reached the CLI's internal-error shield, which reported a Pebble bug instead of the documented range-cap error.
- **Decision**: Compute the number of values with Python integer arithmetic in `_range_length`, for positive and negative steps, and compare that count to the cap before constructing the list. A range too large to allocate now raises the same positioned "range would produce N values" EvalError as any other oversized range, with N printed exactly. The language surface and the cap itself are unchanged.
- **Consequences**: Huge but legal integer bounds fail through the normal error contract, and the message can contain a count up to the integer-digit cap. Costs: one arithmetic helper must stay in step with Python's range semantics; tests cover huge positive, stepped and negative ranges plus the formatted-error corpus.

### ADR-009: String and list concatenation share the sequence length cap
- **Date**: 2026-10-22
- **Status**: Accepted
- **Context**: ADR-003 caps ranges and repeated sequences at 1,000,000 values so memory stays predictable, but `+` joined two strings or two lists without checking their combined length. `len("x" * 1000000 + "y")` returned 1,000,001, and a loop can double a sequence until the host runs out of memory. Concatenation was the remaining unbounded sequence constructor.
- **Decision**: `+` on two strings or two lists computes the combined length first and refuses a result over `MAX_SEQUENCE_LENGTH` with a positioned EvalError ("joining these strings/lists is too large") that names the exact length and the cap. A result exactly at the cap is allowed. Repetition and range keep their existing checks.
- **Consequences**: Every user-visible sequence constructor now respects one memory bound. Costs: a program that built a larger sequence by joining two pieces now gets an error; the check adds one length addition per string or list `+`.

### ADR-010: v5 adds four guarded text builtins: split, join, trim and replace
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-001 froze the surface and ADR-002 fixed the builtin contracts, and ADR-004 added `float()`. Pebble can read script arguments and index and slice strings, but it cannot cut text into fields, put fields back together, clean surrounding whitespace or rewrite a fragment. Every text-processing script therefore grows a hand-written loop over indices, and those four gaps are the ones users reach for first.
- **Decision**: Add four builtins to the global scope, each with a fixed arity and positioned errors in the ADR-002 style. `split(text)` splits on runs of ASCII whitespace (space, tab, newline, carriage return, form feed and vertical tab) and drops the leading and trailing runs, so no field is empty; `split(text, separator)` splits at every exact non-empty separator and keeps empty fields. Both return a list of strings, refuse a non-string text, a non-string separator and an empty separator, and the two-argument form refuses a result of more than MAX_SEQUENCE_LENGTH pieces. `join(values, separator)` joins a list of strings with a separator, refuses a non-list, a non-string element (naming its index) and a non-string separator, and refuses a combined length over MAX_SEQUENCE_LENGTH with the same cap and wording as string `+` (ADR-009). `trim(text)` removes leading and trailing ASCII whitespace from that same set and leaves the interior untouched. `replace(text, search, replacement)` rewrites every non-overlapping occurrence left to right, refuses a non-string argument and an empty search, and refuses a computed result length over MAX_SEQUENCE_LENGTH. This amends ADR-002's builtin list, which now has fourteen names; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: Real text scripts become four calls instead of hand-written index loops, and every new sequence constructor stays inside the existing memory bound. Costs: the surface grows by four names; `split` and `trim` use an explicit ASCII whitespace set rather than Python's Unicode set, so a non-breaking space is data rather than a separator; a list of non-strings must be converted element by element; there is no split limit, no case folding and no regular expressions.

### ADR-011: v6 adds sort(values), the list ordering that reuses the min/max rules
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-002 fixed the builtin contracts and defined the ordering `min`/`max` use: numbers with numbers, strings with strings, everything else refused. ADR-010 then added `split`, whose natural result is a list of fields, but Pebble can only take a list's extreme values, not order it. Ranking a list therefore means a hand-written nested loop with an index and a swap, the last ordinary list operation scripts still write by hand, and a descending order needs the same code again.
- **Decision**: Add one builtin, `sort(values)`: it accepts a list and returns a new ascending list of its values, leaving the argument untouched. Ordering is exactly the ADR-002 rule `min`/`max` already apply: numbers order with numbers by value and strings order with strings by code point; a non-list argument, a value that is not a number or string, and a list mixing kinds are positioned EvalErrors with the wording `min`/`max` use. An empty list returns an empty list. The sort is stable, so equal values keep their relative order. Descending order needs no argument: the existing slice form composes as `sort(values)[::-1]`. This amends ADR-002's builtin list, which now has fifteen names; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: A list can be ranked in one call, and `sort` composes with `split`, `join` and slices instead of growing a direction or comparator parameter. Costs: the surface grows by one name; there is no descending flag, no key function and no reverse builtin (a reverse slice covers them); sorting is not capped by a new limit because the result is the same size as the already bounded argument.

### ADR-012: v7 adds case folding, contains and find, with a none result instead of a sentinel
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-010 gave text one shape and ADR-011 gave lists an order, but Pebble still cannot compare text without caring about case, ask whether one string occurs inside another, or locate a fragment. Every such program hand-writes an index loop, and the obvious host convention for a missing match, `-1`, is the same value that means "last character" in `s[i]`, so a caller cannot tell a miss from a real index.
- **Decision**: Add four builtins in the ADR-002 style, each with a fixed arity and positioned Why/Fix errors. `upper(text)` and `lower(text)` return the text with every character's case mapped by the host's Unicode-aware mapping (so `upper("ß")` is `"SS"`), refuse a non-string, and refuse a result longer than MAX_SEQUENCE_LENGTH with the result length named. `contains(text, search)` returns a bool: whether the search text occurs anywhere. `find(text, search)` returns the zero-based character index of the first occurrence, or `none` when it is absent, so a miss can never be mistaken for a negative index. Both search builtins refuse a non-string argument and an empty search text, matching the empty-separator and empty-search rule `split` and `replace` already state. This amends ADR-002's builtin list, which now has nineteen names; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: Case-insensitive matching becomes `contains(lower(text), lower(needle))`, and a located fragment can be compared against `none` before it is used as an index. Costs: case folding can change a string's length, so its cost is bounded by the same cap; there is no case-insensitive search flag, no `starts_with`/`ends_with`, and no regular expressions; `find` returns the first match only, so later matches need a slice.

### ADR-013: v8 adds starts_with, ends_with and count, with one non-empty search rule
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-012 gave Pebble `contains` and `find`, which answer where a fragment sits, but not whether text begins or ends with one, and not how often it occurs. A prefix check therefore compares slices by hand, a suffix check does index arithmetic with `len`, and a frequency count needs a walking loop that has to get the step right to stay non-overlapping. `split`, `replace`, `contains` and `find` already refuse an empty search text, so a new edge or counting builtin should follow that rule rather than invent a second one.
- **Decision**: Add three builtins with a fixed arity of two and positioned Why/Fix errors. `starts_with(text, prefix)` and `ends_with(text, suffix)` return a bool and compare by characters, not bytes, so a Unicode prefix works. `count(text, search)` returns how many non-overlapping occurrences appear, counted left to right, which is what `str.count` does: `count("aaa", "aa")` is 1, not 2. All three refuse a non-string argument and an empty prefix, suffix or search, with a Why that names the consequence (an empty part matches everywhere, so the predicate is always true and the count is endless) and a Fix that says to pass a character or drop the call. Counting returns an int bounded by the text's length, so no new limit is needed. This amends ADR-002's builtin list, which now has twenty-two names; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: Prefix and suffix validation and a frequency count are one call each, and the empty-argument rule is now uniform across all six search-shaped builtins. Costs: `count` counts text only, so counting equal list elements still needs a loop; there is no case-insensitive variant (fold with `lower` first); and an overlapping count such as `count("aaa", "aa")` returning 1 must be documented, which the ADR and a test now do.

### ADR-014: v9 adds sum(values), sharing the int and float caps of arithmetic
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-011 gave lists an order and ADR-002 already lets `min`/`max` order numbers with numbers, ints with floats. Pebble can therefore inspect a list but cannot total it, so every score, size or cost total is a hand-written accumulator loop, the last ordinary numeric list operation left to scripts. A total also has to respect the two bounds arithmetic already promises: ADR-003 caps an int near 4,000 digits and ADR-006 refuses a non-finite float.
- **Decision**: Add one builtin, `sum(values)`, with a fixed arity of one and positioned Why/Fix errors. It accepts a list of numbers, where a number is an int or a float but not a bool, matching `is_number` everywhere else. The result is an int when every value is an int and a float once any value is a float, so the int/float distinction survives the total. `sum([])` is `0`. A non-list argument and any element that is not a number are refused, naming the element's index and stating that booleans are not numbers. The result then passes the same bounds arithmetic passes: an int over the bit cap is refused with the arithmetic wording, and a float total that is not finite is refused as too large for a float. This amends ADR-002's builtin list, which now has twenty-three names; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: A list of numbers totals in one call with predictable typing and the same memory bound as `+`. Costs: there is no `average` or `product` (an average needs a zero-length rule and a float division, so it waits for its own ADR); `sum` does not coerce numeric strings, so text must be converted with `int` or `float` first; and negative-zero or float rounding follows the host exactly as `+` already does.

### ADR-015: a seeded crash fuzz guards the no-traceback promise
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-001 promises that every user-triggered failure is a positioned Pebble report with a Why and a Fix, ADR-003 adds a CLI shield that turns an unexpected host exception into a three-line report, and ADR-006, ADR-008 and ADR-009 each closed a path that reached a traceback. Those guarantees are checked today only by hand-written cases in `test_hardening.py`. Each new builtin (ADR-010 to ADR-014) adds a fresh surface where a host exception could escape, and a hand-written corpus only proves the cases someone thought of.
- **Decision**: Add `tests/test_fuzz.py` as a deterministic guard. Its corpus comes from a fixed seed, so every failing sample reproduces exactly: random token soup from a small alphabet, typed structured programs that mostly parse and run, every tracked example program, and single-token replacements, drops and duplications of those examples. Each sample must either run or raise `PebbleError`; a leaked `RecursionError` or any other host exception fails the test with the sample text. A separate check runs the same soup through `cli.main` and asserts an exit code of 0, 1 or 2 and that the internal-error shield never fires. Every resource cap the sample can reach is patched down (call depth, sequence and range length, exponent, integer digits) so a hostile sample stays cheap, and the structured corpus must produce at least 60 successful runs out of 120 to prove it still exercises the runtime rather than only the parser. `random` from the standard library is the only new import.
- **Consequences**: A crash in the lexer, parser, evaluator or CLI shield is now caught by the suite within a fixed, reproducible seed instead of by a user. Costs: the seed is a pinned choice, so a rerun after editing the generator can shift the corpus and needs the floor re-checked; the caps are patched, so the fuzz does not prove the real limits hold (the dedicated cap tests still do); and the module adds about half a second to `python -m unittest discover`.

### ADR-016: v11 adds average(values), the mean ADR-014 deferred
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-014 added `sum` and recorded an average as deliberately deferred, because a mean needs a zero-length rule that a total does not: `sum([])` is a defensible `0`, while the mean of nothing has no value at all. In the meantime every script that wants a mean writes `sum(xs) / len(xs)` and must remember to guard the empty list itself, which is exactly the kind of rule the language should state once.
- **Decision**: Add one builtin, `average(values)`, with a fixed arity of one and positioned Why/Fix errors. It accepts a non-empty list of numbers, where a number is an int or a float but not a bool, and returns the mean as a float always, even when the list holds one int. An empty list is a positioned EvalError ("average needs at least one value") rather than `0` or `none`, because there is nothing to divide by. A non-list and any non-number element are refused with the same wording and index that `sum` reports, through one shared helper so the two builtins cannot drift apart. The result must be finite: an average beyond the largest float is refused as too large, and an int whose mean has no float value is refused with the same message through a guarded division rather than a host `OverflowError`. This amends ADR-002's builtin list, which now has twenty-four names; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: A mean is one call with a stated empty-list behaviour, and `sum` and `average` share one element rule. Costs: the surface grows by one name; the always-float result means `average([1, 3])` prints `2.0` rather than `2`, so an integer mean needs `int(...)`; the division is guarded because an int inside Pebble's digit cap can still be far larger than any float, a case the first implementation would have surfaced as a traceback, and the fuzz corpus now includes such an integer.

### ADR-017: v12 adds round(value[, digits]) with half-up ties, not host rounding
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-002 fixed nine builtins and ADR-004 added `float()`; `floor` exists but nothing rounds to the nearest value. Every formatted number therefore hand-writes `floor(x + 0.5)`, which is wrong for negative values (`floor(-2.5 + 0.5)` is `-2`, not `-3`) and cannot round to a decimal place at all. The host offers `round`, but it rounds ties to even, so `round(2.5)` is `2` there while every school rule users bring says `3`; inheriting that default would make Pebble's arithmetic surprising in a way no error message can explain.
- **Decision**: Add `round(value)` and `round(value, digits)` as one builtin with one or two arguments. Both accept an int or a float but not a bool, and refuse a non-finite float. `round(value)` returns the nearest int, and `round(value, digits)` returns a float, so the result type follows the request rather than the input. Ties round away from zero (`round(2.5)` is `3`, `round(-2.5)` is `-3`), computed with `decimal` from the value's shortest decimal form and `ROUND_HALF_UP`, so decimal-looking input behaves as written (`round(2.675, 2)` is `2.68` rather than binary-error `2.67`). `digits` must be an int from 0 to 15 with bools refused; a negative or larger count is a positioned error, because a float carries at most that many useful decimal places here and the digit count never extends to integer places. An int passed with a digit count is already exact, so it returns as a float when representable and reports a float-overflow error when it is not; an int alone passes through unchanged. This amends ADR-002's builtin list, which now has twenty-five names; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: Rounding to a whole number or a decimal place is one call with a stated tie rule, and the negative-value bug of the hand-written idiom disappears. Costs: the surface grows by one name; `decimal` joins `math` and `re` as a standard-library import; `round` deliberately disagrees with Python's `round` on ties, so a reader importing Python habits must read this ADR; rounding is decimal-based rather than IEEE-based, so it is slower than `math.floor` and its 40-digit working precision is a documented internal choice rather than part of the contract.

### ADR-018: v13 adds list search, and Pebble equality moves to one shared definition
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-011 gave lists an order and ADR-014 and ADR-016 gave them totals, and ADR-012 gave text `contains` and `find`. Pebble can therefore search text but not a list, so every membership check is a hand-written loop with a found flag, and a position needs a second variable. `==` already defines Pebble equality precisely (ADR-002's comparison rules: ints and floats mix, bools do not, everything else compares within its own type, lists compare deeply), but that definition lives in `evaluator.py`, and a builtin cannot import it without a cycle because the evaluator imports the stdlib.
- **Decision**: Move the equality rule to `formatting.values_equal`, which both `evaluator._equal` and the new builtins call, so `==` and list search cannot drift. Add one builtin, `index_of(values, value)`: it takes a list and any value, returns the zero-based index of the first element equal to the value, and returns `none` when no element matches, following ADR-012's decision that a miss is `none` rather than `-1`. A non-list first argument is a positioned EvalError. Extend `contains` to accept a list as its first argument and answer whether any element equals the second argument; the text form keeps its existing contract, including the refusal of an empty search text, and a first argument that is neither a list nor a string is refused with the `contains needs a string, got <type>` wording it already uses. Searching a list never restricts the value's type: `contains(["a"], 1)` is simply `false`. This amends ADR-002's builtin list, which now has twenty-six names, and ADR-012's `contains` contract; every other v1 contract stands, including the three-line positioned error format.
- **Consequences**: Membership and position on a list are one call each, and one equality rule now serves `==`, `contains` and `index_of`. Costs: `contains` is polymorphic over two kinds, so its error text must be read carefully; a list search is linear with no index argument, so finding every match still needs a loop; and moving equality touched `evaluator.py`, which is why this ADR records it rather than leaving it as a refactor detail.

### ADR-019: pyproject.toml is the declared version, and a test holds the runtime to it
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: `pyproject.toml` declared version `0.2.0`, while `pebble/__init__.py` carried `__version__ = "0.1.0"`, so `python -m pebble --version` reported a version the package was never declared at. Nothing in the suite compared them: the existing CLI test asserted the literal string `pebble 0.1.0`, which pinned the stale value instead of catching the drift. A user reporting a bug against `--version` output would therefore name the wrong release.
- **Decision**: Make `pyproject.toml`'s `[project] version` the declared version and set `__version__` to match it, which fixes the reported version to `0.2.0`. Add `test_the_reported_version_matches_the_packaging_metadata`, which reads `pyproject.toml` and compares its version to `pebble.__version__`, and change the CLI version assertion to derive its expectation from `__version__` rather than hard-code a literal. The test reads the manifest with a regular expression rather than `tomllib`, because the project supports Python 3.10 and `tomllib` arrives in 3.11. A future release bumps `pyproject.toml` first and the test then forces `__version__` to follow.
- **Consequences**: `--version` now names the declared release, and a packaging bump can no longer leave the runtime behind. Costs: the version still lives in two files, so a release edits both (the test makes the pair mandatory rather than automatic); the test's regex assumes the single-line `version = "x.y.z"` form that `pyproject.toml` uses; and this record does not choose a new release number, it adopts the one packaging already declared.

### ADR-020: v15 declares version 0.3.0, which describes the shipped surface
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-019 made `pyproject.toml` the declared version and aligned `__version__` to its `0.2.0`, which fixed the reporting bug without asking whether that number was still true. Since `0.2.0` was declared, ten increments landed: ADR-010 to ADR-014 and ADR-016 to ADR-018 added sixteen builtins (`split`, `join`, `trim`, `replace`, `sort`, `upper`, `lower`, `contains`, `find`, `starts_with`, `ends_with`, `count`, `sum`, `average`, `round`, `index_of`), ADR-015 added the seeded fuzz guard, and the surface moved from ten builtins to twenty-six. A user reading `pebble 0.2.0` cannot tell any of that, and the number cannot mark the release it describes.
- **Decision**: Declare `0.3.0` in `pyproject.toml` and set `__version__` to it, so `python -m pebble --version` reports `pebble 0.3.0`. This is a minor bump, not a major one: every change since `0.2.0` adds to the frozen v1 surface under its own ADR (ADR-001's rule that an addition needs a new task and a new ADR), and no v1 contract was broken — `split` and `replace` refuse new cases, `round` is new rather than changed, and the moved equality rule preserves `==` behaviour exactly. ADR-019's coherence test is the guard that the bump reached both files.
- **Consequences**: The declared version now matches what a user actually gets, and the next release has a stated baseline. Costs: the version lives in two files, so a release still edits both (the test makes the pair mandatory, not automatic); this record does not tag or publish anything, so the `0.3.0` marker exists only in the source tree until a release task uses it.

### ADR-021: v13.1 corrects nested list equality and large-float rounding
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-018 moved equality into `formatting.values_equal` and added list search, but the shared function delegated list comparison to Python's `==`, so nested bools compared equal to nested numbers even though ADR-002 says bools do not mix. ADR-017's `round` used a fixed 40-digit decimal context, so a finite float with a large exponent, such as `float(10 ^ 300)`, was refused even though its rounded value is representable. Both cases were found while auditing the v13 history.
- **Decision**: Compare lists element by element with `values_equal` so nested values follow the same equality rule as top-level values. Size the decimal context to the input's adjusted exponent plus the digit count, with a floor of 40 digits, so large finite floats round instead of failing. Add regression tests for nested bool/number lists and for `round(float(10 ^ 300))` and `round(float(10 ^ 300), 2)`. This corrects the implementation to the contracts ADR-002 and ADR-017 already state; it adds no builtin and changes no other rule.
- **Consequences**: `[[true]] == [[1]]` is now false, `contains([[true]], [1])` and `index_of([[true]], [1])` no longer match, and large finite floats round successfully. Costs: list equality is now recursive in Python rather than a single C-level comparison, so deeply nested lists are slower; the decimal context can grow with the exponent, though it remains bounded by the finite float range.

### ADR-022: v9.1 closes the mixed int/float sum overflow
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-014 promised that a `sum` result outside the float range is a positioned "too large for a float" error. `sum(values)` on a list holding a huge int and a float made Python convert the int to a float, which raised `OverflowError`; the CLI shield then reported an internal error instead of a Pebble report. The audit of the v9 history found the gap.
- **Decision**: Catch `OverflowError` around the total and raise the same positioned "the result is too large for a float" EvalError that a non-finite float total uses. Add a regression test with `sum([10 ^ 3990, 1.5])`. This completes ADR-014's stated guard; it adds no builtin and changes no other rule.
- **Consequences**: A mixed huge-int/float total now reports a normal Pebble error, and the no-traceback promise holds for this path. Costs: the guard is one more explicit exception path, and a program that wants an approximate total must scale its values or convert deliberately.

### ADR-023: v4.1 closes the mixed int/float arithmetic overflow
- **Date**: 2026-10-29
- **Status**: Accepted
- **Context**: ADR-006 requires every arithmetic result to be finite and every user failure to be a positioned Pebble report. Adding, subtracting, multiplying or taking the remainder of a huge int and a float made Python convert the int to a float before the result checks ran, so `OverflowError` escaped to the CLI shield. The audit of the v4 hardening history found the gap.
- **Decision**: Catch `OverflowError` around the numeric result in `_add`, `_numeric`, `_multiply` and `_remainder`, and raise the same positioned "the result is too large for a float" EvalError that a non-finite float result uses. Add a regression test covering `+`, `-`, `*` and `%` with `10 ^ 3990` and a float. This completes ADR-006's guard; it adds no operator and changes no other rule.
- **Consequences**: Mixed huge-int/float arithmetic now reports a normal Pebble error, and the no-traceback promise holds for these paths. Costs: each numeric operator carries one explicit exception path, and a program that wants an approximate result must scale its values or convert deliberately.
